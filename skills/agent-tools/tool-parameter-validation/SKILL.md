# Model-Generated Tool Parameter Validation

Reviews agentic AI systems for validation of tool parameters generated by the model. Aligned with **OWASP Agentic AI ASI08 (Tool Misuse)**, **CWE-20 (Improper Input Validation)**, and the AWS Well-Architected Agentic AI Lens best practice **AGENTSEC02-BP02: Validate tool inputs and outputs**.

## The Core Issue

Validating only user-facing parameters while trusting what the LLM emits to the tool is the default bug in most agent implementations. An attacker who can influence the model through prompt injection can make the model emit tool arguments that no user ever typed. If the only validation happens upstream of the model, those arguments reach the tool unchecked.

Four validation layers matter, each at a different stage:

1. **Model layer** — constrained decoding (strict mode, `additionalProperties: false`, enums) stops malformed parameters at the source.
2. **Pipeline layer** — JSON Schema validation inside the tool handler stops malformed parameters that slip past the model.
3. **Policy layer** — a policy engine evaluates business rules on parameter values before the tool executes.
4. **Logic layer** — automated reasoning or domain-specific checks validate relationships between parameters.

No single layer is sufficient. The model layer can be bypassed by API clients that don't use the SDK; pipeline validation can miss business rules; policy enforcement can miss logical constraints.

## 1. When to Use

Invoke this skill when:

- **Reviewing MCP tool integrations.**

- **After a prompt-injection finding** where the exploitation path was through tool arguments.

## 2. What to Detect

| Signal | Pattern | Confidence |
|---|---|---|
| Tool handler consumes model output directly | `def tool_x(**kwargs):` or equivalent that doesn't validate `kwargs` before use | HIGH |
| No JSON Schema check in Lambda / handler | Handler does not load a schema and call `validate(kwargs, schema)` or equivalent | HIGH |
| Strict tool use not enabled | Tool definition does not set `strict: true`, `additionalProperties: false`, or enum constraints on closed-set fields | MEDIUM |
| User input and model-generated args share the same validator | Single validation step at the HTTP boundary; tool handlers trust what they receive | HIGH |
| Error responses leak internals | Tool catches exceptions and returns the raw traceback or internal path | MEDIUM |
| No size/pagination limit on tool output | Tool returns arbitrarily large responses to the agent without truncation logging | LOW |
| No timeout / memory limit | Lambda / handler has default or unbounded timeout and memory | MEDIUM |
| No policy check at the gateway | Tool is reached through a gateway but no policy evaluates parameter values | MEDIUM |

See [`patterns.md`](patterns.md) for language-specific detection patterns (Python, TypeScript, Java, Go).

## 3. Rules (Constraints)

- **MUST** verify every tool invocation path validates the parameters the model generates, not only the parameters the user provided.
- **MUST** verify at least one explicit schema check runs inside the tool handler (defense-in-depth beyond the model's constrained decoding).
- **MUST** verify structured outputs / strict tool use is configured where the SDK supports it.
- **MUST** verify tool error responses do not expose stack traces, internal paths, or infrastructure identifiers.
- **MUST** verify tool output size is bounded and any truncation is logged so the agent is not reasoning on silently truncated output.
- **MUST** verify Lambda / handler timeout and memory are right-sized based on measured execution profiles.
- **MUST NOT** flag input validation done at an API gateway alone as sufficient — validation must also happen for model-generated parameters inside the tool handler.
- **MUST** map every finding to a real control ID from a `frameworks` entry.

## 4. Remediation

When machine-readable output is requested, findings MUST be available as JSON that validates against [`schemas/finding.schema.json`](../../../schemas/finding.schema.json). See [`docs/normalized-json-output.md`](../../../docs/normalized-json-output.md).

**Before (vulnerable):**

```python
# src/tools/reschedule_appointment.py
def reschedule_appointment(appointment_id, new_time, reason=None):
    # Trusts whatever the model produced
    db.execute(
        f"UPDATE appointments SET scheduled_at = '{new_time}' WHERE id = '{appointment_id}'"
    )
    if reason:
        send_email(to=db.query("SELECT patient_email FROM appointments WHERE id = ?", [appointment_id])[0],
                   subject="Appointment rescheduled",
                   body=reason)  # reason flows straight into user-facing email
    return {"status": "ok"}
```

**After (remediated):**

```python
# src/tools/reschedule_appointment.py
from jsonschema import validate, ValidationError
from datetime import datetime, timezone

SCHEMA = {
    "type": "object",
    "additionalProperties": False,
    "required": ["appointment_id", "new_time"],
    "properties": {
        "appointment_id": {"type": "string", "pattern": "^appt_[A-Za-z0-9]{10,32}$"},
        "new_time": {"type": "string", "format": "date-time"},
        "reason":    {"type": "string", "maxLength": 500}
    }
}

MAX_RESCHEDULES_PER_APPOINTMENT = 3
MIN_NOTICE_HOURS = 2

def reschedule_appointment(**kwargs):
    # 1. Schema validation (pipeline layer — complements model's strict tool use)
    try:
        validate(kwargs, SCHEMA)
    except ValidationError as e:
        return {"status": "error", "category": "invalid_arguments"}  # sanitized error

    # 2. Logical constraints (logic layer)
    new_time = datetime.fromisoformat(kwargs["new_time"])
    if new_time < datetime.now(timezone.utc).replace(hour=datetime.now(timezone.utc).hour + MIN_NOTICE_HOURS):
        return {"status": "error", "category": "insufficient_notice"}

    # 3. Business rule (policy layer)
    count = db.query_scalar(
        "SELECT reschedule_count FROM appointments WHERE id = %s", [kwargs["appointment_id"]]
    )
    if count is None:
        return {"status": "error", "category": "not_found"}
    if count >= MAX_RESCHEDULES_PER_APPOINTMENT:
        return {"status": "error", "category": "reschedule_limit_reached"}

    # Parameterized query (not string interpolation)
    db.execute(
        "UPDATE appointments SET scheduled_at = %s, reschedule_count = reschedule_count + 1 WHERE id = %s",
        [new_time, kwargs["appointment_id"]]
    )

    # 4. Output sanitization — email body uses a templated phrase,
    #    not model-provided text
    if kwargs.get("reason"):
        send_email(
            to=get_patient_email(kwargs["appointment_id"]),
            subject="Appointment rescheduled",
            template="appointment_reschedule",
            template_args={"new_time": new_time.strftime("%B %d, %Y at %H:%M %Z")}
        )
    return {"status": "ok"}
```

Tool definition for the agent must also use strict mode:

```json
{
  "name": "reschedule_appointment",
  "strict": true,
  "input_schema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["appointment_id", "new_time"],
    "properties": {
      "appointment_id": {"type": "string"},
      "new_time":       {"type": "string", "format": "date-time"},
      "reason":         {"type": "string"}
    }
  }
}
```

## 5. Verification (falsifiable)

| | |
|---|---|
| **Input** | Any agent repository with tool handlers |
| **Expected output** | Finding(s) for any tool handler missing explicit schema validation, with evidence |
| **Pass condition** | Every tool handler loads a schema and validates `kwargs` before using them, and the tool definition uses strict mode with `additionalProperties: false` |
| **Fail condition** | At least one tool handler uses `**kwargs` or equivalent without validation, OR a tool definition omits strict mode / `additionalProperties`, OR error responses expose stack traces |

## 6. Gotchas (self-improvement loop)

**False positives**

- **Pattern:** A tool handler that accepts `**kwargs` but immediately passes them to a second function that validates. **Why:** Validation happens, just not inline. **Suppress:** Confirm the receiving function has an explicit schema check within one call frame.
- **Pattern:** Tools behind an API Gateway that validates the schema at the HTTP layer. **Why:** HTTP-layer validation is good, but prompt-injection attacks can originate from inside the agent and never cross the HTTP boundary. **Suppress:** Only if the tool is exclusively reachable via HTTP from external callers and the agent cannot invoke it directly.
- **Pattern:** Internal tools exposed only to a single agent with constrained decoding and strict mode enabled. **Why:** The model can't emit invalid parameters in this path. **Suppress:** Verify strict mode is on and the SDK enforces it.

**Precision traps**

- **Trap:** Requiring JSON Schema validation inside the handler can conflict with Pydantic / dataclass-based parameter parsing in frameworks like Strands or LangChain. **Mitigation:** Pydantic model validation counts — the pattern is "explicit validation before use", not "jsonschema library specifically".
- **Trap:** Adding `additionalProperties: false` to an existing tool can break callers that pass legitimate extra fields. **Mitigation:** Review each tool's observed call pattern before enforcing, and allow a migration period where unknown fields are logged but not rejected.

**Do NOT flag:**

- Handlers in test fixtures (`**/tests/**`).
- Example code clearly marked as such (`examples/`, `demo/`).
- Internal helper functions not registered as tools.
